## 모드 C — 보고서 검토·수정 (방법론)

기존 보고서(hwpx/텍스트)의 검토·첨삭·레드팀 요청이면 이 모드.
**착수 전에 `references/review_methodology.md` 전문을 읽고 그대로 따른다.** 요지:

- **역할 = 검토자 + 레드팀.** 위치·원인·대안 제시가 기본이고, 직접 수정은 사용자가
  명시적으로 요청할 때만. 결정권은 항상 사용자 — 조직 관행·상급자 방침이 지침보다
  우선한다.
- **순서 = 구조 → 블록 → 문장 → 표기.** 하위를 다듬다 상위 문제가 드러나면 상위로
  되돌아간다. 착수 시 보고서가 인용하는 상위 문서(규정 등) 원문을 함께 확보한다.
- **모든 지적에 근본 원인 진단**을 붙인다. 대안은 결이 다른 2~3개 + 추천 1개 +
  **최소 수정안 포함**. 상급자 확정 단어는 재론하지 않고 고정 제약으로 흡수한다.
- **버전마다**: diff 리뷰(합의 반영 → 무단 변경 → 회귀) · 인용 원문 대조 · 숫자
  실측 · 파급 검사(수정 지점을 참조하는 모든 위치). **최종 선언 전**: diff 와
  독립적인 전문(全文) 재스캔을 마친 뒤에만 "이슈 0건"을 말한다 — 그 전에는
  "diff 기준 이상 없음"과 구분해 말한다.
- **보고 형식**: 공표 전 필수 → 강력 추천 → 취향 순으로 우선순위를 매기고, 취향은
  취향이라고 명시해 결정을 넘긴다. 잘된 변경은 이유와 함께 인정한다.

### 메모로 주고받기 (`scripts/review_memo.py`)

한/글 메모(F4 로 열리는 그 메모)를 코드로 달고 읽는다. 실무에서 돌아다니는
검토본이 정확히 이 모양이다 — 지적이 지적당한 자리에 붙어 있다.

```python
import sys, os
sys.path.insert(0, os.path.join("<스킬 폴더>", "scripts"))
from review_memo import annotate, read_memos

# ① 받은 검토본에서 남이 단 지적을 회수
for m in read_memos(r"C:\...\사업계획서_검토본.hwpx"):
    print(m["number"], m["author"], m["anchor"], "→", m["text"])

# ② 내 검토 의견을 달아 돌려주기
res = annotate(r"C:\...\사업계획서.hwpx", [
    {"anchor": "운영 기록, 설비 사진 등",
     "text": "[데이터]\n어느 데이터를 쓰는지 확인필요"},
    {"anchor": "공용 인프라", "text": "[인프라]\n협조 여부 확인필요"},
], author="검토자")
# {"status", "added", "skipped", "path"} — path 는 `<원본이름>_메모.hwpx`
```

- **원본은 덮어쓰지 않는다.** 새 파일로 나온다(원본과 대조할 수 없으면 검토가
  무의미하다). 다른 이름을 원하면 `out_path=` 를 준다.
- **anchor 는 본문에 있는 글자 그대로**여야 하고, 한 조각(`hp:t`) 안에 통째로 들어
  있어야 한다. 탭으로 열을 맞춘 일정 줄처럼 쪼개진 줄이면 **앵커를 더 짧게** 잡는다.
- 같은 말이 여러 번 나오면 `"nth": 2` 로 몇 번째인지 고른다.
- **못 찾은 앵커는 `res["skipped"]` 에 사유가 남는다** — 조용히 빠지지 않는다.
  돌려주기 전에 반드시 `skipped` 가 비었는지 확인한다.
- 메모 본문은 첫 줄에 `[데이터]` 처럼 분류를 달고 다음 줄에 지적을 쓰는 것이
  실무 관행이다(돌아온 검토본이 그렇게 쓴다).
- **메모를 단다고 검토 보고가 대체되지는 않는다.** 우선순위를 매긴 검토 결과는
  그대로 전달하고, 메모는 그 결과를 문서에 얹는 수단으로 쓴다.
